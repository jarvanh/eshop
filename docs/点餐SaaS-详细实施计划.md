## 1. 项目概述

本项目是多租户餐饮点餐 SaaS。**以 ruoyi-vue-pro（master-jdk25 分支，JDK 25 + Spring Boot 4.1，MIT 协议）为技术底座——系统管理、多租户、支付、会员、商品、优惠券、公众号等基础能力直接复用底座；商品规格、优惠券、积分商城、素材库等业务模块从 yshop-drink（MIT）移植；桌台多人协同、收银台、预约、骑手、财务提现等无成熟开源实现的核心能力自研**（覆盖率实证见 §4.2，逐功能途径见 §2 映射总表）。实施采用「AI 编码代理 + 人工审核」模式（见 §1.4）。

### 1.1 项目定位

| 项    | 内容                                                                 |
| ---- | ------------------------------------------------------------------ |
| 项目类型 | 餐饮点餐 SaaS：扫码点餐（堂食/外卖/自取/预约）+ 收银 + 营销 + 多租户运营                       |
| 商业模式 | 多租户 SaaS，卖给商家，平台收订阅费                                               |
| 技术底座 | ruoyi-vue-pro master-jdk25（JDK 25 + Spring Boot 4.1，MIT），**不从零开发** |
| 实现途径 | 底座复用 / yshop 移植 / 自研 / 三方 SDK（见 §2 实现总纲）                           |
| 部署形态 | Docker Compose 起步，单体模块化，后期可按模块拆分                                   |
| 资金合规 | 支付走商家自有商户号（普通商户模式），平台不经手订单资金；商家/骑手提现属代发场景，见《AI-工程手册》6.5                    |

### 1.2 功能范围（来自 xlsx，三端结构）

功能范围以《点餐系统功能清单.xlsx》为准，产品终态为**五端一云**：

| 端     | 形态                      | 核心内容                                                                                 |
| ----- | ----------------------- | ------------------------------------------------------------------------------------ |
| 后台管理端 | Web（平台运营用）              | 装修、工作台、收银台、桌台、门店、商品、订单（堂食/外卖/自取/预约/收银五类）、会员、骑手、营销、统计、财务、支付、快递、消息、微信管理、基础设施、系统管理、租户管理 |
| 门店端   | Web（门店员工用，同后台不同角色/数据权限） | 工作台、收银台、门店中心（桌号/打印机/广告/收支/提现/桌面分类/预约标签/规则）、商品中心、订单中心、营销中心                            |
| 顾客移动端 | uniapp（小程序/H5）          | 首页、点餐、购物车、订单（含扫码继续加餐）、支付、优惠券、用户中心、积分商城、门店、提前预约、桌台扫码（单人/多人协同）                         |
| 商家中心  | uniapp 内商家角色页           | 数据面板、桌台协助点餐、菜品管理、订单实时+出单打印、商家提现、我的管理                                                 |
| 骑手中心  | uniapp 内骑手角色页           | 首页数据、接单大厅、收入明细、历史订单、提现                                                               |

### 1.3 关键决策记录（ADR）

| #  | 决策                                              | 理由                                                                                                                             |
| -- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| D1 | **底座用 ruoyi-vue-pro（单体完整版，master-jdk25），不从零开发** | system/infra/pay/member/mall/mp/promotion/trade 覆盖基础能力 60%+；MIT；社区最大。yshop 本身即芋道同源 fork（表结构 system\_*/infra\_* 同构），业务模块移植对齐成本低 |
| D2 | 不用 yudao-cloud 微服务版                             | 4 人团队养不起 Nacos/Gateway/Seata 全家桶                                                                                               |
| D3 | master-jdk25（JDK25 + SB4.1）起步                   | SB 3.5 OSS 支持 2026-06-30 已结束；day-0 升级最便宜；上游已正式适配。M0 设半天决策门，红灯退 master-jdk17                                                    |
| D4 | 多人协同点餐自研（服务端权威）                                 | 无任何开源实现可抄（见 D6 实证）；产品差异化护城河                                                                                                    |
| D5 | 支付走普通商户模式                                       | 平台不经手订单资金，规避二清                                                                                                                 |
| D6 | **yshop-drink 开源版只作部分移植源，缺口全部自研**（详见 §4.2 实证）   | 上游完整开源版经源码核验为 open-core：骑手/提现/会员卡购买/预约/桌台/收银挂单/打印机管理等均为商业版功能，开源仓库无实现                                                           |
| D7 | **不购买 yshop 商业版授权，分期自研缺口**                      | 商业版为 SB3/JDK17 技术栈，迁移到芋道 jdk25 底座仍需大量适配；且长期演进绑定其架构。改为 P0/P1/P2 分期（§5.0）控制节奏。**若团队后续评估工期不可接受，此决策可复议（买断价 vs 4 人月成本对比）**          |
| D8 | **门店端不单独开发第二套管理端**                              | 同一 Vue 后台 + 角色菜单/数据权限（门店角色仅见本店），芋道 RBAC 原生支持                                                                                   |
| D9 | **外卖配送双轨制：初期第三方同城配送（UU 跑腿等），骑手自配送放 P2**         | 骑手体系（入驻/调度/提现/骑手端）是完整子系统，MVP 不应被它阻塞                                                                                            |

### 1.4 实施模式：AI 主力实现 + 人工审核

本项目采用「AI 编码代理 + 人审核验收」的人机协作模式：

| 角色        | 职责                                                                                     |
| --------- | -------------------------------------------------------------------------------------- |
| AI（编码代理） | 按功能 ID 接单：按「实现方式」列选择途径（芋道复用/yshop 移植/自研）→ 写代码+测试 → commit+push 到 GitHub 私有仓库 → 更新跟踪表状态。**全部执行规则见《AI-工程手册》** |
| 人（项目负责人） | 派单（手册 §0 启动提示词 / §5 任务模板）、敏感域逐行复核（见 §6.4 红线表）、里程碑验收、合并 main、方向决策                                  |

**四文档分工**：本计划=项目怎么管（人看）→ 工程手册=AI 怎么干（AI 看）→ 跟踪表=做到哪 → 核验报告=什么不能碰。所有上下文都在文档里，AI 会话可随时中断重开而不丢失信息。

**给 AI 的四条铁律**（全文见《AI-工程手册》§1）：禁止造轮子（动手前先查实现方式）→ 禁止编造三方 API 参数 → 完成即测试（禁止积压）→ 测试通过立即 commit+push（禁止攒代码）。

### 2.4 覆盖率结论

- **芋道底座直供**：约 45 项（系统/基础设施/微信/支付/会员/订单骨架）

- **yshop 开源可移植**：约 15 项（商品规格三表、券、积分商城、快递、素材、广告、服务菜单、门店基础）

- **必须自研**：约 55 项（桌台体系、协同、收银挂单、打印、预约、骑手、提现、财务、会员卡购买、工作台、统计）

- 三方 SDK：快递100、UU跑腿、易联云/飞鹅、高德/腾讯定位、微信全家桶

**开源版没有**（xlsx 清单里的以下功能在开源仓库零实现，属商业版）：

- 骑手全套（rider/courier 关键词命中 0）

> 结论：**xlsx ≈ yshop-drink 商业版功能矩阵；开源版约覆盖 1/3**。此实证是 D6/D7 决策的依据。
